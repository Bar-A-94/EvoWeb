# `data/` — the EvoWeb datasets

All files are JSON Lines, one app per line. **Sample index = 1-based row position** in the file a
run used: `result.json["index"] == 7` means line 7, and the scorer keys per-sample task counts by
line position (`evoweb/scoring.py:load_expected_tasks`). Never re-sort a dataset.

## Files

`evoweb_benchmark.jsonl` and `multilingual/` are not committed: they are downloaded, the latest
version each time, from [Hugging Face](https://huggingface.co/datasets/TD-Labs/EvoWeb) by `evoweb/paths.py:ensure_data`
(scoring, the tests and every harness run call it; `python3 -m evoweb.paths` does it by hand).
A local copy is used when the download fails. `harness/run_local.sh` pins one revision for the whole
run (`EVOWEB_HF_REVISION`, default the latest commit at launch); `EVOWEB_NO_DOWNLOAD=1` keeps local
files (e.g. your own `assemble.py` output) instead of re-downloading them.

| file | rows | what it is | paper element |
|---|---|---|---|
| **[`evoweb_benchmark.jsonl`](https://huggingface.co/datasets/TD-Labs/EvoWeb)** | 32 | **the benchmark**: 32 apps, a build request and 9 follow-up requests each, with the judge's checks | Tables 2 and 4, Figures 3 and 4, App. F |
| [`multilingual/evoweb_benchmark_<lang>.jsonl`](https://huggingface.co/datasets/TD-Labs/EvoWeb) | 32 | the benchmark with the user's requests translated into French, German, Chinese, Hindi or Hebrew (`fr de zh hi he`); the app and the judge's checks stay in English | Table 3 |
| `ablation_no_grounding.jsonl` | 30 | the ablation: 30 of the benchmark apps with follow-up requests written without the real-website corpus | App. C.1 |
| `legacy_webgen_bench_apps.jsonl` | 101 | the WebGen-Bench base apps: build prompt and judge tasks, no follow-ups | source of every first request |
| `similar_websites.json` | 101 entries | the grounding corpus: per app (`app_idx`), real similar websites with `name`, `url`, `what_it_does` and `interesting_features` | input to the request generator; App. C.1 |

`evoweb_benchmark.jsonl` and the ablation set were written by the generator workflows in
`data/data_gen/` (see its README); `python3 data/data_gen/audit_parts.py data/evoweb_benchmark.jsonl --quiet`
re-runs the mechanical audit on a committed set. The translations are regenerated byte for byte by
`python3 data/data_gen/multilingual/assemble.py --out-dir <dir>` from the parts in
`data/data_gen/multilingual/parts/`. `python3 harness/make_tasksets.py` writes small smoke sets
into `tests/smoke_sets/` (not committed). `tests/test_datasets.py` checks all of it.

## Schema of one row

Keys of a row of `evoweb_benchmark.jsonl`:

```
id                  "000001"   zero-padded WebGen-Bench app id; NOT the sample index (see above)
instruction         the first (build) request
Category, application_type      WebGen-Bench metadata, unused by the harness
ui_instruct         [ {task, expected_result, task_category{primary_category, subcategories[]}} ]
                    the judge's checks for the first request (4-9 per app)
follow_ups          [ 9 x {                                   request k = follow_ups[k-2], k = 2..10
    archetype       derived-state | multi-surface-workflow | interactive-tool | design-restyle
    instruction     the user's request
    source_website, source_feature      the real product feature the request was grounded in
                    (the no-grounding set carries `feature_rationale` instead)
    ui_instruct     [ 5 x {kind, task, expected_result, task_category, [copied_from_request]} ]
  } ]
dependency_graph    {nodes: [{id: "R1".."R10", label, archetype}],
                     edges: [{from, to, what}]}        what = the concrete thing `to` relies on
global_rules        [ 3 x {rule, introduced_in_request} ]  app-wide rules the requests introduce
pinned_seed         {entity, introduced_in_request (2 or 3), records_gist, [records]}
                    records, when present, is a string (JSON-encoded where it is a list)
                    the fixed demo data every exact-value check is written against
target_app_summary  prose description of the app the 10 requests build towards
```

The rows of `legacy_webgen_bench_apps.jsonl` carry only the first five keys; the benchmark rows
are 32 of them with the rest added.

## The five checks of every follow-up request

Every follow-up request carries exactly five judge checks in a fixed order (`task_idx` 0-4):

| task_idx | kind | what it verifies |
|---|---|---|
| 0, 1, 2 | `exact-value` or `feature` | **functional**: the request's own feature; `exact-value` pins a number, ordering or label derived from the pinned seed data |
| 3 | `integration` | **integration**: the new feature combined with one built earlier, along an edge of `dependency_graph`. When the request has **no incoming edge** the check verifies one of the `global_rules` instead (18 of the 288 follow-up requests); Table 4 scores those separately |
| 4 | `backward` | **backward**: a check copied from an earlier request (`copied_from_request`), to see whether the earlier feature still works |

The first request is judged with the row's own `ui_instruct` (WebGen-Bench's original checks).
